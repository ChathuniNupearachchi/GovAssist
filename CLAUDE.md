# GovAssist

A mobile app that resolves a Sri Lankan citizen's specific government
service situation into a personalised, source-traced document checklist.
Not a chatbot — the output is a verifiable plan the citizen can act on.

## What it does

Takes a citizen's situation (via chat or guided questions), evaluates it
against verified government rules, and produces:

- A personalised document checklist with every item sourced and dated
- The exact fee computed for their case
- The specific office that accepts their application
- Prerequisites flagged in the order they must happen

## Two kinds of question, two mechanisms

This distinction is the core of the architecture. Do not collapse them.

**Open questions → an agent with tools.**
"What's the process for a lost passport?" "Should I amend my passport
or get a new one?" These are answered by a tool-using agent that
chains together retrieval and read-only calls into the rules engine —
`retrieve_documents`, `get_fee`, `find_office`, `get_next_question`,
`resolve_case`, `compare_amendment_vs_renewal` — and composes an
answer from their results. A comparison question needs more than one
tool call in the same turn (two fee lookups plus a document lookup, or
the dedicated comparison tool) — that's the point, not an edge case.
The agent never computes a fee, office, timeline, or requirement
itself; every such value in its answer is verified against what a
tool call actually returned that turn, the same reject-and-retry-once-
then-fall-back-to-an-explicit-non-answer discipline citation
verification already used for retrieved chunks.

**Situation questions → Rules engine.**
"I'm 34, my name changed after marriage, I'm applying from Kandy —
what do I need?" These are answered by evaluating conditions against
the citizen's answers, computing the fee, routing to the correct office,
and ordering prerequisites. Retrieval cannot do this reliably. The
intake conversation itself gets two presentation-only touches — a
recorded fact is acknowledged before the next question, and the next
question's surface wording may be rephrased for context — neither
changes which question gets asked or what gets recorded; that stays
`next_question.py`'s deterministic decision and `CASE_ANSWER`'s literal
content respectively.

The plan output is always generated by the rules engine, never by the
agent. The agent's tools happen to call into the engine for numbers —
it composes prose, it does not decide what those numbers are; the
engine remains the sole producer of the deliverable.

## Why this is not a wrapper

A general model can find passport requirements. It cannot evaluate ten
branching variables against one person's situation and tell you which
gazette said so. The rules engine holds conditional logic in data —
adding a rule is a database insert, not a deployment.

## How the LLM APIs are used

Six jobs, split across two providers by one rule (`langgraph-
orchestration-branch`'s cost-engineering decision, driven by this being
a fixed-budget student project): **the tool-using agent that composes
citizen-facing answers is the only output anyone actually sees and is
judged on, so it alone stays on Claude — a paid model, chosen for
quality.** Every other job is evaluation, ingestion, or presentation
work that runs on every turn (or off the citizen-facing path entirely)
regardless of what the citizen sees next, so it runs on Gemini's free
tier instead. Provider selection is a config value, not a code
choice — see `app/llm/gateway.py` (LiteLLM) and `LLM_MODEL_<JOB>` env
vars — so any of these can be moved back to Claude, or to any other
LiteLLM-supported provider, without touching a call site.

Still narrow regardless of provider — every job either extracts/
classifies existing text, or composes prose around values a
human-auditable computation (the rules engine, retrieval, or a direct
database read) already produced. None of them decides a fee, office, or
requirement:

1. Parsing scraped text into structured draft rules (never live) —
   currently still Claude; not yet routed through the gateway
2. Classifying a citizen's chat message: intent (situation, question, or
   answer), any facts it states, and whether it also asks a question —
   never a fee, office, or requirement. **Gemini's free tier**
   (`app.chat.classifier`, job `classify`).
3. Answering an open question as a tool-using agent: selecting which of
   six read-only tools to call (retrieval and rules-engine lookups
   among them), possibly chaining several in one turn, and composing
   the final prose — every fee/office/timeline/requirement value it
   states is verified against what a tool call actually returned that
   turn, structured output the same way job 2's classification is.
   **Claude** (`app.chat.agent`) — the one job kept there; see above.
4. Extracting text from scanned PDFs when there is no text layer for
   pdfplumber to read — OCR-by-LLM, not a citizen-facing job. Scanned
   PDFs are common in Sri Lankan government sources generally, not just
   Immigration, so this recurs across departments. **A free three-stage
   chain first** (pdfplumber's text layer, then Tesseract OCR — free,
   local, unlimited — then Gemini Flash vision only if Tesseract's
   output fails a quality check), **Claude as a last resort** behind
   `PDF_OCR_CLAUDE_LAST_RESORT_ENABLED` if every free stage fails
   (`app.ingestion.pdf_extraction`).
5. Rephrasing an intake question's surface wording for conversational
   fit — never which attribute it asks about (that's `next_question.py`,
   untouched) or what a citizen's answer records to. **Gemini's free
   tier** (`app.chat.rephrase`, job `rephrase`).
6. Acknowledging a fact the citizen just stated, and — only when the
   rules engine's own before/after diff shows it — naming a requirement
   that fact newly triggered; never a fee or office, and never a fact
   or requirement the engine didn't actually record or compute. **Gemini's
   free tier** (`app.chat.acknowledge`, job `acknowledge`) — not one of
   the branch's originally-named jobs, but the same profile as 2 and 5,
   so moved for the same reason.

Every job routed to Gemini keeps its original fallback path unchanged
(a low-confidence or failed classification still defaults to a question
with no recorded fact; a failed rephrasing or acknowledgement still
falls back to the canonical prompt or no acknowledgement at all) — a
free tier being rate-limited or unavailable degrades a turn, it never
errors one.

Citizens never receive ungrounded LLM output. Every generated answer
(single-shot or tool-composed) cites the source chunks and/or tool
results it was built from, and that grounding is verified — not just
trusted — against what was actually retrieved or returned before the
answer is returned; a fabricated or missing citation, or a value no
tool call actually produced, is rejected and retried once, then falls
back to the same explicit non-answer weak retrieval produces. If
nothing relevant is found, or nothing can be verified, the system says
so rather than guessing. This holds regardless of which provider
generated the answer — citation verification is not Claude-specific.

## RAG layer

- Scraped pages and PDFs are chunked into retrievable passages. Tables
  and lists are detected during extraction and kept as one structured
  chunk each (markdown, never split), instead of being flattened into
  undifferentiated prose — the mechanism adapts to what a given source
  actually uses (HTML `<table>`, `<ul>/<ol>`, or label-value paragraph
  pairs), not one fixed markup assumption
- Every chunk carries metadata (document title, section heading, content
  type, source URL). Only the text passed to the embedding model is
  prefixed with a compact context header built from that metadata — the
  stored, citizen-facing chunk text stays raw
- Chunks are embedded locally with sentence-transformers
  (all-MiniLM-L6-v2, 384 dimensions) and their text is also indexed for
  Postgres full-text search; embeddings and the full-text index live in
  the same table as the relational rules
- Retrieval ranks candidates with a hybrid of vector similarity and
  full-text relevance, blended by reciprocal rank fusion, so an exact
  identifier ("Form K-35A", "section 19(2)") and a semantic paraphrase
  are both handled by whichever signal is actually good at it
- Every chunk keeps a foreign key to its SOURCE_DOCUMENT, so retrieved
  answers carry the same citation and verified-as-of date as checklist items
- Retrieval is scoped to approved document versions only — draft content
  is never retrievable
- Generation is forced into a structured schema and every citation it
  returns is verified against the set of chunks actually retrieved for
  that call; a citation outside that set, or no citation at all, is
  rejected and retried once before falling back to an explicit
  "no relevant match" response — the same response weak retrieval itself
  produces, so a citizen sees one consistent failure mode
- Every chat message, in either direction, is persisted (the audit trail
  of what a citizen was actually told) and a returning device resumes
  its most recent unresolved case rather than starting over; Redis
  caches the active case's recent messages and answered facts as a fast
  path, with Postgres as the durable record

## React Native Rules

- React Native only. No web APIs, no DOM, no div/span.
  Use View, Text, Pressable.
- NEVER pass a function to the style prop. NativeWind does not apply it.
  Use plain style objects. Track pressed state with onPressIn/onPressOut
  - useState.
- Do not combine className with a style function on the same element.
  Prefer the style prop with tokens.
- All colours, spacing, radii and font sizes from src/theme/tokens.ts.
  Never hardcode values.
- Minimum touch target 48px (touchTarget.min).
  Minimum body font size 16px (fontSize.body).
- Every interactive element needs accessibilityRole and accessibilityLabel.
  Checkboxes and toggles also need accessibilityState.
- Component variants are string unions with a lookup object, not booleans.
  Good: variant?: "primary" | "secondary"
  Bad: isPrimary?: boolean
- TypeScript strict. No any.
- Every data surface handles four states: loading, empty, error, loaded.
- Export new components from src/components/index.ts.
- Use Ionicons from @expo/vector-icons. Never use emoji as icons.

## Backend Rules

- Every requirement shown to a citizen must have a source_document_id
  and a verified_at date. No requirement is generated without a
  verified source.
- Every RAG answer must cite the chunks it was generated from, and those
  chunks carry their source document and verified date.
- Scraped content never goes live automatically. It creates a draft
  version that a human reviewer must approve before publishing.
- Retrieval only searches approved versions. Drafts are invisible to citizens.
- Embeddings run locally with sentence-transformers. No GPU required.
- All endpoints that call the LLM are rate-limited.
- Approving a rule version has four consequences: write the new version,
  re-embed affected chunks, invalidate caches, flag affected saved plans.

## Users

Sri Lankan citizens, including older and less technical people,
often anxious about a government process and using the app
outdoors on a phone. Plain language, no jargon, generous
spacing, high contrast.

## Content Rules

- Every requirement carries its source and a verified-as-of date.
- Never state a fee, document or deadline without a verified source.
- The app gives guidance, not an official ruling. Say so where it matters.
- A wrong checklist is worse than no checklist. When retrieval or the
  engine cannot ground an answer, say so rather than guessing.

## Out of Scope

- Sinhala and Tamil — English only
- Online submission or payment
- Appointment booking
- Citizen accounts (device storage only; optional Google sign-in for sync)
- Departments beyond Immigration (Phase 1)
